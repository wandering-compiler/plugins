# Contributing

## Layout

```
<plugin>/
├── plugin.yaml          the manifest: name, version, features, the w17 range it supports
├── README.md
├── proto/               the plugin's declarations (types/, queries/, mutations/, business/, …)
└── src/                 the Go module: handlers, libraries, tests
    └── gen/             GENERATED by `make gen` — never edited, never committed
tools/                   release, the names check, the pinned w17ctl and golangci-lint versions, the lint config
```

## The checks

Every pull request runs them, and `main` merges only when the `ci-ok` check is
green. Run them locally with Go, docker and a w17ctl login (`make gen` asks the
console):

| | what it checks |
|---|---|
| `make gen` | not a check: generates every plugin's `src/gen` (below); each target that compiles Go runs it first |
| `make fmt` | gofmt over the hand-written Go |
| `make vet` / `make test` | `go vet`, and the tests with coverage |
| `make lint` | golangci-lint with `tools/golangci.yml`, at the version pinned in `tools/golangci-version`: unchecked errors, `==` on errors that may be wrapped, dead code, staticcheck, gosec and the rest of the set the config names |
| `make check-committed-pb` | committed pb outside `src/gen` — a directory with its own `buf.gen.yaml`, e.g. `cluster/src/workerpb` — is exactly what its proto generates |
| `make check-modules` | each `go.mod` is tidy, with no `replace` onto a local path |
| `make check-stage` | no Go file references a declaration that only another feature's files bring, and no DQL statement names a table, column or request field that only another feature adds (ungated) — a consumer enabling one feature without the other would not build |
| `make check-plugin-msgids` | the `//w17:msgid` sentences in the Go and the `msgids:` block of `plugin.yaml` agree (`make plugin-msgids-sync` rewrites the block from the Go) |
| `make check-render` | the installable form renders with the pinned w17ctl: inert Go, tests carried, no `src/gen` |
| `make check-published-tests` | the tests pass from the rendered form too, rehydrated as a reader would (`src/gen` generated from the rendered `plugin.yaml` and `proto/`) |
| `make check-refs` | nothing cites the w17 platform's private repository (its docs, its source tree) — state the reason in place |
| `make check-names` | no file, and no file path, names a real project (see below) |
| `make check-tools` | the repository's tool modules and any plugin sandbox module are gofmt-, vet- and lint-clean, and pass |

`make check` runs them all, and `PLUGIN=<name>` narrows any of them to one plugin.

CI runs one more check that has no local target: **adoption**. Every public
example (the `examples` repository) is generated, built and tested with the
plugins of the pull request in place of the ones it vendors, so a change that
breaks a project using a plugin fails here, not after a release. It needs the
`W17_TOKEN` secret, so it fails for a fork's pull request the same way
`check-names` does.

A pull request that changes only Markdown (`tools/docs-only.sh`: no other
file, and no Markdown file deleted or moved) skips the per-plugin checks and
adoption. `check-refs`, `check-names` and the changelog check still run, and
`ci-ok` passes. A push to `main` always runs everything.

**`src/gen` is generated, never written.** `make gen` (`w17ctl plugin gen
<plugin>` at the pinned version) writes all of it from `plugin.yaml` and
`proto/`: the pb, the contract `RegisterPlugin` takes (`EnvConfig` from the
`env:` block, `ClientSet` with a client per storage service plus
`DistributedTransaction`, `Connection` and `AclLock`, `HandlerRegistry` with a
`Register<Svc>Server` per business service plus `RegisterShutdown`) and the
feature constants at the manifest defaults. It is what a consumer's staging
generates for an activation, so the plugin compiles here against the same
shape. Never edit it and never commit it (`.gitignore`); change `plugin.yaml`
or a proto and run `make gen` again. Document a configuration entry in its
`description:` in `plugin.yaml` — it becomes the field's comment — and, where a
plugin needs only part of `ClientSet`, declare the narrow interface in the
package that uses it. `make gen` needs the console: a w17ctl login locally,
the `W17_TOKEN` secret in CI — so, like adoption, the plugin checks fail for a
fork's pull request.

A directory with its own `buf.gen.yaml` (e.g. `cluster/src/workerpb`) is not
`src/gen`: its pb is committed, and `make check-committed-pb` regenerates it
with buf and compares.

**The render** is `w17ctl plugin render` at the version pinned in
`tools/w17ctl-version`, and `make gen` uses the same binary; `tools/w17ctl.sh`
installs exactly that version, and the checks never use whatever `w17ctl` is on
your PATH. Bump the pin in a pull
request.

## Changelog

A pull request that changes a plugin adds `<plugin>/changes/<name>.md`: a
`### ` heading naming the change and a few lines on what a user of the plugin
has to know. Do not edit `CHANGELOG.md`; the release collects the fragments
(RELEASING.md). A change nobody using the plugin can notice (tests, comments)
takes the `no-changelog` label instead.

## Tests

A plugin is the part of w17 other people's projects run, so its tests are the
contract. Cover the edge cases, not only the happy path: refusals, expiry,
concurrency, malformed input. The coverage summary of every run is on the
pull request's checks page.

## Keep it anonymous

This repository is public. Fixtures, examples, comments and test data use
obviously invented names (`acme`, `example.com`, `tenant-a`), never a real
company, customer or project, not even one that uses w17. `make check-names`
enforces it against a list held as a CI secret. A finding prints the file and
line, never the name.

A pull request from a fork does not receive that secret, so its `ci-ok` stays
red. A maintainer brings the branch into this repository to get it checked.
