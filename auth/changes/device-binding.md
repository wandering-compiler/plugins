### Every token is bound to a device key (breaking)

A session used to be a bearer token that worked from anywhere until it expired. Now every token is bound to the device that signed in: a key pair its client holds, identified by the RFC 7638 thumbprint of its public key. The client proves it holds the key on every request with a DPoP proof (RFC 9449); the gateway verifies the proof and passes the plugin only the thumbprint.

- **Every existing session is refused once.** Sessions issued before this version carry no binding, so the next request with one is refused (`DEVICE_PROOF_REQUIRED`) and the person signs in again, one time. API tokens issued before it are refused the same way. Later upgrades do not sign anybody out.
- **Clients must send DPoP proofs.** A bound token goes as `Authorization: DPoP <token>` with a `DPoP` proof header; every sign-in request (`SignIn`, `SignUp` when it issues a session, `ConfirmSignUp`, `VerifyMfa`, `OAuthExchange`, `CliToken`) needs a proof too, and is refused without one before anything else happens. The gateway support comes with the platform release that pairs with this version; the generated TypeScript client, the SDKs and w17ctl sign for you once updated. Deploy them together.
- **New refusals** (`UNAUTHENTICATED`, with an `ErrorDetail` and a `google.rpc.ErrorInfo` in domain `auth.w17`): `DEVICE_PROOF_REQUIRED`, `DEVICE_MISMATCH` (the proof was signed by another key) and `DEVICE_REVOKED` (the device was revoked; the client generates a new key and signs in as a new device).
- **`AuthResp.device_id`** carries the verified device of every authenticated request.
- **Device identity is base tier.** The `Device` table, `UserToken.device_id` and `User.device_trust_revoked_at` exist in every activation. The `devices` feature is now only the management endpoints (`ListDevices`, `RevokeDevice`, `RevokeOtherDevices`, `RevokeAllDevices`); revoking a device stamps `Device.revoked_at` instead of deleting the row, so the key stays refused for good. `two_factor_scope=new_devices` works without `devices`, and trust belongs to the (account, device) pair.
- **Removed:** the `X-Device-Id` and `X-Device-Trust` headers, the device trust token (`device_trust_token` on `SignInResp`, `VerifyMfaResp` and `OAuthExchangeResp`), `Device.identifier`, `Device.trust_token_hash`, and the storage rpcs `GetDeviceByIdentifier`, `CreateDevice`, `TouchDevice` and `DeleteDevice` (replaced by `RegisterDevice` and `MarkDeviceRevoked`). `IssueToken` now requires `device_id`.
- **`CreateApiToken` and `IssueBotToken` refuse** with `UNIMPLEMENTED` / `DEVICE_KEY_REQUIRED` in this version: an API token must be bound to the key of the program that will use it, and the request cannot carry it yet. The next version adds it.
- **Migration.** Generate and apply a migration: new table `Device` (unique `(user_id, thumbprint)`) and columns `UserToken.device_id` and `User.device_trust_revoked_at` where the `devices` feature was off; where it was on, `Device` loses `identifier` and `trust_token_hash` and gains `thumbprint` (NOT NULL) and `revoked_at`. Rows of the old `Device` table name a client-chosen identifier, not a key, and cannot be carried over: clear them before adding `thumbprint` (their sessions are refused anyway, and every device signs in once as new).
