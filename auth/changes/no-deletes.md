### Nothing in the auth tables is deleted, in any table (breaking)

The revocation work kept tokens, accounts, devices and clients; the remaining sixteen `DELETE` statements — roles, role grants, role permissions, organizations, memberships, invitations, pending sign-ups, authenticators and recovery codes — are now state changes too. The rows stay as the history, and every read skips ended rows, so what callers and permission checks see is what the delete gave. A test now refuses any `DELETE` in any auth proto or in the plugin's Go.

- **How a removed key is reused.** A table whose key must be reusable after a removal gets an `ended_key` column (`''` while live, the row's own id once ended) inside its unique index: `Role (name, ended_key)`, `Organization (slug, ended_key)`, `OrgMembership (user_id, org_id, ended_key)`, `UserRole (user_id, role_id[, org_id], ended_key)` (all three variants), `UserTotpSecret (user_id, ended_key)`. Re-adding is the same INSERT and creates a new row; the ended row is never rewritten. `Role.name` and `Organization.slug` are no longer unique on their own (a deleted role's name and a deleted organization's slug can be taken again, as before). `RolePermission` keeps its `(role_id, permission_id)` index — the platform's role seed upserts on it — and revives instead: see below.
- **rbac.** `DeleteRole` stamps `Role.deleted_at`, revokes every grant of the role, frees its name and clears its `preset_key` (the next role seed recreates a deleted preset as a new row, as before); its permission rows stay. `RevokeRoleFromUser` stamps `UserRole.revoked_at` and takes an optional `revoked_by`. `RemovePermissionFromRole` stamps `RolePermission.removed_at` and takes an optional `removed_by`. `AddPermissionToRole` is an UPSERT: it revives a removed pair, and **adding a permission the role already carries answers the existing row instead of `AlreadyExists`** (`RolePermissionAdded` is emitted for it too); it takes an optional `added_by`. Both permission calls append to the new append-only table `RolePermissionChange` (`role_id`, `permission_id`, `kind` ADDED/REMOVED — new enum `RolePermissionChangeKind` — `changed_by`). `UpdateRole` refuses a deleted role (NotFound). Every role and permission query skips deleted roles, revoked grants and removed permissions; **`GetUserPermissions` now joins `Role`**, so a deleted role's permissions are no longer reported (it used to keep granting them).
- **org_membership.** `DeleteOrganization` stamps `Organization.deleted_at`, removes the organization's memberships and revokes its org-scoped grants, and frees its slug. **`DeleteOrgMembership` is renamed `MarkOrgMembershipRemoved`** (optional `removed_by`; `AuthService.RemoveOrgMembership` passes the caller): it stamps `removed_at` / `removed_by` and revokes the member's org grants with the same actor. `UpdateOrgMembership` takes an optional `changed_by` (passed by `UpdateOrgMembershipRole`), recorded as `revoked_by` on the grants a role change replaces. `UpdateOrganization` refuses a deleted organization. Every organization and membership query skips ended rows, so a deleted organization's `owner_id` grants nothing.
- **org_invite.** **`DeleteOrgInvite` is renamed `CloseOrgInvite`** (optional `closed_by`; `RevokeOrgInvite` passes the caller) and **`ClearExpiredOrgInvite` `CloseExpiredOrgInvite`**: both stamp `OrgInvite.closed_at`. The pending index becomes `(org_id, email) WHERE accepted_at IS NULL AND closed_at IS NULL`. A closed invitation is refused like a spent one and is not listed; the invitation readers also skip a deleted organization's.
- **sign_up_confirmation.** `ClaimPendingSignUp` is `UPDATE … SET claimed_at = NOW() … RETURNING` (still exactly-once). **`DeletePendingSignUpsForEmail` is renamed `SupersedePendingSignUpsForEmail`** (stamps `superseded_at`), and **`PurgeExpiredPendingSignUps` is removed** — SignUp no longer purges; an expired registration stays, refused by its `expires_at`. New eraser `ErasePendingSignUpAddress`: an erasure (`EraseUsers`) now also ends the address's pending registrations and replaces their address and hashes, since they are no longer deleted at confirmation.
- **two_factor.** **`DeleteTotpSecret` is renamed `RevokeTotpSecret`**: it stamps `UserTotpSecret.revoked_at` and clears `seed` and `secret`; **`DeleteRecoveryCodes` is renamed `RevokeRecoveryCodes`**: it stamps `UserRecoveryCode.revoked_at` on the unused codes. A revoked authenticator verifies nothing and a revoked code is refused like a used one. `TotpDisabled` still fires on both disable and re-enrolment.
- **Events** keep their names and payloads.
- **Migration.** Generate and apply a migration: new columns `Role.deleted_at`, `Role.ended_key`, `RolePermission.removed_at` / `removed_by`, `UserRole.revoked_at` / `revoked_by` / `ended_key` (rbac); table `RolePermissionChange` (rbac); `Organization.deleted_at` / `ended_key`, `OrgMembership.removed_at` / `removed_by` / `ended_key` (org_membership); `OrgInvite.closed_at` / `closed_by` (org_invite); `PendingSignUp.claimed_at` / `superseded_at` (sign_up_confirmation); `UserTotpSecret.revoked_at` / `ended_key`, `UserRecoveryCode.revoked_at` (two_factor). The unique indexes listed above are replaced. No data changes: every existing row is live (`ended_key` `''`, every new state column NULL).
- **Outside this plugin** the platform's role seed still prunes `RolePermission` rows with a `DELETE`, and cannot revive a pair `RemovePermissionFromRole` removed: a seeded permission removed at runtime stays removed until it is added again.
